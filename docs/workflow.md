# Как работаем экономно (Claude / Codex / DeepSeek)

Записано после разбора, куда уходят токены Claude Pro. Причина не «долгая
история чата», а: `app.py` — ~280 тыс. токенов, из них 75% — HTML/JS в
строках; читать это целиком дорого, а каждый раунд диалога пересылает
контекст заново. План ниже — как этого избегать.

## Разделение труда

| Кто | Что делает | Почему |
|---|---|---|
| **Claude** | архитектурные решения, «почему не работает и никто не понял», ревью чужих правок, точные ТЗ для Codex, злые баги (гонки, TDZ, эстафеты состояния между окнами) | дорогой по токенам, но решает то, что дешёвые модели не тянут |
| **Codex** (через ChatGPT Plus) | рефакторинг по готовому ТЗ, перенос шаблонов в файлы, массовые правки, рутинные тесты Playwright | объём дешёвый, для механической работы качества хватает |
| **DeepSeek** (бесплатный) | объяснить кусок кода, накидать черновой CSS/regex/SQL, разобрать текст ошибки, помочь найти нужное место в коде по grep-выдаче | лимиты не мои, для «понять/разобрать/накидать черновик» достаточно |

DeepSeek как «улучшатель промпта для Claude» почти бесполезен: сам промпт
весит десятки-сотни токенов, а чтение кода и ответ — тысячи-десятки тысяч.
Экономия там мизерная. Смысл DeepSeek — снять с Claude задачи, которые
вообще не должны были до него доходить.

## Модель и режим внутри Claude Code

- **Sonnet по умолчанию** (`/model sonnet`) — правки CSS, текста, понятные
  баги, добавить кнопку. Opus на Pro съедает лимит намного быстрее.
- **Opus** — только когда нужна архитектурная голова: гонки состояний,
  решения вроде эстафеты плеера между окном/вкладками, разбор непонятной
  ошибки, которую Sonnet не находит с первого захода.
- **Reasoning effort на Medium/Low** для обычных задач, **High** — только
  под реально сложные баги. High думает платными токенами, для «поправь
  отступ» это чистый слив.

## Как экономить внутри одной задачи

1. **Указывай место в коде.** «Поправь плеер» → модель ищет и читает
   тысячи строк. «В `app.py`, функция `vg_player_js`, кнопка `data-pip`»
   (найти самому: `grep -n "data-pip" app.py`) → читает пару сотен строк.
2. **Одна тема — один чат, потом `/clear`.** Каждый ход в диалоге
   пересылает всю историю заново; десятый ход в длинном чате стоит куда
   дороже первого. Но не дробить ОДНУ задачу на несколько чатов — тогда
   модель каждый раз заново читает тот же код с нуля.
3. **Полное ТЗ сразу**, включая «а ещё чтобы на телефоне». Каждый круг
   «ой, добавь ещё» — это пересылка всей истории плюс повторное чтение
   файлов.
4. **Не проси «проверь, всё ли ок на сайте»** — это чтение мегабайта кода
   и/или дорогой Playwright-прогон. Проверяй сам через `scratchpad/run.sh`,
   приноси модели конкретную ошибку текстом (из консоли браузера, из
   `jscheck.py`, из логов).
5. **Playwright и скриншоты — по требованию, не по умолчанию.** Дорогая
   проверка нужна перед мержем в main или для правда непонятного визуального
   бага — не как рутинная перепроверка каждой мелкой правки.
6. **Не звать субагентов на рутину.** Каждый агент стартует с нуля и
   заново вычитывает контекст — удвоение расхода без выгоды на простых
   задачах.
7. **Считай не сообщения, а раунды инструментов.** Реальная правка кода —
   это чтение → правка → проверка → возможно ещё раз. Чем точнее задача
   сформулирована с самого начала, тем меньше раундов.

## Гигиена `CLAUDE.md`

`CLAUDE.md` читается на КАЖДОМ раунде каждой сессии — его размер умножается
на число раундов задачи, а не платится один раз. Держать там:
- как проверять правки (команды, ловушки, которые кусали дважды);
- **текущее** состояние фич (что реализовано и как это работает сейчас);
- жёсткие ограничения хозяина.

НЕ держать в `CLAUDE.md`: историю «попробовали X → откатили → попробовали
Y → откатили → вернули X» — это ценно как урок, но не нужно на каждый
раунд диалога. Такое — в `docs/history.md`, читать по требованию, когда
задача реально касается той темы.

## Разрез `app.py`

Главный структурный рычаг — файл физически слишком большой, чтобы читать
его целиком было дёшево. План разреза на шаблоны + blueprints — в
`docs/codex-refactor-plan.md`, это задача для Codex, не для Claude
(объёмная, но механическая).
