# План: убрать структурный долг + дисциплина документации

Этот файл самодостаточен: новый чат (Claude или Codex) читает его и
работает по нему, ничего не помня из прошлых сессий. Задачи 31-40 —
продолжение нумерации из `docs/codex-onboarding.md` (там были 1-30,
разрез `app.py` на `templates/` + `blueprints/`, все выполнены).

## Что уже сделано раньше (не переделывать)

- HTML/JS вынесены в `templates/*.html` (читаются через `_template()`,
  БЕЗ Jinja2 — обычные файлы + `.replace()`).
- Роуты разложены по `blueprints/*.py` (17 файлов, фабрики
  `create_X_blueprint(...)`).
- Версии зависимостей зафиксированы в `requirements.txt`.
- Есть автотесты: `tests/`, 15 файлов, ~2400 строк, гоняются в CI дважды
  (до слияния в main и перед сборкой на VPS).
- Деплой переехал на раннер прямо на VPS в Амстердаме.

## Замеры на 2026-09-18 (почему этот план вообще существует)

| Что | Значение |
|---|---|
| `app.py` | 4837 строк, 184 функции верхнего уровня (2540 строк), 204 глобальных присваивания |
| `create_drop_blueprint(...)` | **61 зависимость** аргументами. `remote` — 45, `ai` и `backup_sebastian` — по 33, `home` — 31 |
| `CLAUDE.md` | **72 КБ** (~13 тыс. токенов на КАЖДУЮ сессию). 2026-09-04 был урезан до 20 КБ — вырос в 3.5 раза за две недели |
| из них раздел «Что сейчас работает» | 36 тыс. символов = 78% файла |
| роутов | 175 (две недели назад — 127) |

**Диагноз.** Blueprints получили роуты, но не самостоятельность: логика и
состояние остались в `app.py` и раздаются наружу пачками аргументов.
Правка в дропе = читать `blueprints/drop.py` (793 строки) + блок
регистрации на 61 строку + сами функции в `app.py`. «Одна фича — один
файл» выполнено формально, а не фактически. Плюс главный документ снова
раздулся и грузится целиком независимо от задачи.

## Жёсткое ограничение, которое нельзя нарушить

`app.py` — **не фабрика**: он выполняет всю работу прямо при импорте
(читает пароль из окружения, считает пути к данным от `__file__`,
заполняет глобальные словари). На этом держится вся обвязка тестов
(`tests/conftest.py` импортирует КОПИЮ проекта во временной папке).

**Не превращать `app.py` в фабрику (`create_app()`) в рамках этого
плана.** Модули `core/*` — тоже обычные модули, выполняющиеся при
импорте: семантика не меняется, `conftest.py` продолжает работать без
правок. Если `conftest.py` пришлось править — значит что-то пошло не
так, остановиться и спросить.

# Дисциплина документации (правила для ВСЕХ будущих чатов)

Этот раздел задача 31 копирует в `CLAUDE.md` целиком. Он существует
потому, что за две недели `CLAUDE.md` вырос с 20 КБ до 72 КБ, а опись
роутов дважды разошлась с кодом.

**Куда что писать:**

| Что | Куда | Предел |
|---|---|---|
| Правила, ловушки, ограничения хозяина, навигация «куда идти» | `CLAUDE.md` | ≤ 25 КБ, сторожит тест |
| Как устроена конкретная фича | `blueprints/<name>.md` рядом с кодом | 30-60 строк |
| «Пробовали X, откатили, вот почему» | `docs/history.md` | только если урок повторяемый |
| План/ТЗ | `docs/<name>-plan.md`, после выполнения — пометка «выполнено» | — |
| Список роутов, размеры, счётчики | **никуда** — генерируется скриптом | — |

**Три правила, которые важнее остальных:**

1. **Не писать в документ то, что можно узнать командой.** Число роутов,
   список файлов, размеры — это `grep`/скрипт, а не строчка в `.md`.
   Записанное число устаревает молча и потом врёт увереннее, чем
   отсутствие числа.

2. **Факт, который важен, — сторожить тестом, а не абзацем.** Если
   что-то «нельзя ломать» — на это пишется тест. Пример, который уже
   спас прод: `test_every_url_for_target_exists` ловит `BuildError` от
   переименования эндпоинта при переносе в blueprint (однажды так
   сломался вход в кабинет). Один такой тест полезнее десяти страниц
   описания.

3. **Перед добавлением абзаца в любой `.md` спросить себя:** переживёт
   ли это следующий рефакторинг? если разойдётся с кодом — кто заметит?
   Если ответ «никто» — не писать.

**Чего не делать:**

- не переписывать `CLAUDE.md` целиком «заодно» — дописывать в нужный
  раздел, не заводя новый под каждую фичу;
- не копировать в `CLAUDE.md` описание своей свежей фичи «чтобы не
  забылось» — для этого есть `blueprints/<name>.md`;
- не вести хронику правок в `CLAUDE.md` — она в `docs/history.md`, и
  только если из неё следует урок на будущее;
- не дублировать один факт в двух файлах: копии расходятся, и потом
  невозможно понять, какая верна.

**Когда фича добавляется (напоминание, подробности в CLAUDE.md):**
новый файл в `blueprints/`, разметка в `templates/`, тест в `tests/`,
описание в `blueprints/<name>.md`, опись роутов — перегенерировать
скриптом, в `app.py` — только регистрация.

## Как работать по этому плану

1. Задачи по порядку, **один коммит на задачу** (где не сказано иное).
2. После каждой: `pytest -q` локально, потом пуш и **зелёный CI**
   (он гоняет тесты дважды и реально стучится в живой сайт на VPS).
3. Поведение не меняется байт в байт: те же URL, ответы, заголовки,
   ETag, редиректы, сессии.
4. Если `tests/conftest.py` пришлось править — остановиться и спросить:
   скорее всего, сломана семантика импорта `app.py` (см. «Жёсткое
   ограничение» выше).
5. Не смешивать задачи и не делать попутных правок «раз уж открыл».
