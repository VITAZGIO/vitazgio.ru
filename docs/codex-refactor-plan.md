# ТЗ для Codex: разрез app.py на файлы

## Зачем

`app.py` — 20 099 строк / ~980 КБ / ~280 тыс. токенов, из них 75% (733 КБ)
— HTML/CSS/JS внутри питоновских строк `"""..."""`. Из-за этого любая
правка требует прочитать функцию на тысячи строк (`cabinet()` — 2449
строк, `drop_page()` — 2109, `ai_page()` — 1261, `music_page()` — 1065,
`vg_player_js()` — 996, `diy_page()` — 913), и это дорого по токенам ИИ,
с которым дальше правится код. Цель — тот же функционал, но по файлам
которые можно открыть и прочитать по отдельности.

**Это механическая работа большого объёма — не архитектурный редизайн.**
Поведение сайта не должно измениться ни на пиксель. Каждый шаг —
маленький, проверяемый, коммитится отдельно, чтобы был откат.

## Общая схема

```
app.py                  # только: создание Flask-приложения, конфиг,
                         # регистрация blueprint'ов, before/after_request,
                         # общие хелперы (auth, gzip, etc — то, что
                         # используют все страницы)
blueprints/
  cabinet.py             # роуты кабинета (/cabinet и его API)
  drop.py                 # /drop и /api/drop/*
  music.py                 # /music, /api/music/*, /api/player/*
  ai.py                     # /neuro, /ai, /api/ai/*
  diy.py                     # /diy и его API
  servers.py                   # /servers
  ...по одному blueprint на логический раздел сайта
templates/
  cabinet.html
  drop.html
  music.html
  ai.html
  vg_player.js.tpl        # шаблон /vg-player.js (это JS-ответ, не HTML)
  player_pop.html
  diy.html
  ...
static/
  (без изменений)
```

Разбивку на blueprint'ы бери по разделам сайта (по названиям страниц,
которые уже есть в `CLAUDE.md`), не по произвольному числу строк.

## ВАЖНО: как переносить строки-шаблоны — НЕ через Jinja2 напрямую

Сейчас HTML-строки собираются питоновскими `%%NET%%`-плейсхолдерами и/или
f-строками/`.format()`. Внутри них живёт настоящий JS (например,
`vg-player.js`, `${}` в template literals, JSON-подобные куски). Если
включить для этих файлов обычный Jinja2-рендеринг (`render_template`),
два риска:
1. **Автоэкранирование Jinja** по умолчанию экранирует `{{ }}` — если в
   JS/CSS случайно встретится похожая последовательность, вывод сломается
   молча.
2. Jinja сама использует `{{ ... }}` и `{% ... %}` как синтаксис — если в
   вставляемых Python-переменных (или в самом JS-тексте) есть такие
   последовательности, это может конфликтовать.

**Правило:** переносить шаблоны в отдельные файлы как **обычные текстовые
файлы**, читать их через `Path.read_text()` (или `render_template_string`
только если в файле НЕТ подстановок вообще — тогда просто отдать как
есть) и продолжать делать те же самые подстановки, что сейчас (`%%NET%%`,
`.format()`, f-строки) — **вручную, тем же способом, что в текущем
коде**, а не через `{{ var }}` Jinja. Т.е. `templates/cabinet.html` — это
не Jinja-шаблон, а просто вынесенный кусок строки; код остаётся:
```python
TPL = (Path(__file__).parent / "templates" / "cabinet.html").read_text()
html = TPL.replace("%%NET%%", net_value)  # как сейчас
```
Это устраняет риск полностью и минимизирует диф — меняется только ОТКУДА
берётся строка, а не КАК она собирается.

Если где-то шаблон и правда простой (чистый HTML без опасных совпадений)
— можно оставить как есть, лишний риск того не стоит здесь важнее скорости.

## Ловушки (уже кусали дважды — см. CLAUDE.md)

- `\n` внутри питоновской тройной строки — это НАСТОЯЩИЙ перенос строки и
  ломает JS. При переносе в `.html`/`.js`-файл эта проблема **исчезает
  сама** (в файле `\n` — это просто перенос строки, что и нужно) — но
  ОБЯЗАТЕЛЬНО прогонять `scratchpad/jscheck.py` после каждого переноса,
  чтобы отловить места, где раньше `\\n` был специально задвоен под
  питоновскую строку, а в файле это теперь означает буквальные `\n` в
  выводе (нужно убрать одно экранирование).
- Не переименовывать локальные JS-переменные в процессе переноса «раз уж
  открыл» — например, обработчик Escape нигде не должен зваться `esc`
  (конфликт с глобальным html-экранировщиком, TDZ-баг). Перенос файлов —
  не повод причёсывать код, только раскладка по файлам.
- `/vg-player.js` отдаётся с `private, no-cache` + ETag по md5 текста
  (`make_conditional`) — при переносе в файл ETag считать от содержимого
  ПРОЧИТАННОГО файла (после всех подстановок), логика кэширования должна
  остаться байт-в-байт такой же.

## Порядок (от самого дорогого к дешёвому)

Делать **по одной странице за раз**, каждая — отдельный коммит (лучше
отдельный PR, чтобы можно было откатить один раздел, не трогая другие).
Не переходить к следующей странице, пока текущая не прошла все проверки.

1. `cabinet()` — 2449 строк, самая жирная (133 КБ шаблона).
2. `drop_page()` — 2109 строк.
3. `ai_page()` — 1261 строка.
4. `music_page()` — 1065 строк.
5. `vg_player_js()` — 996 строк (это JS-ответ, не HTML-страница — см.
   примечание про ETag/кэш выше).
6. `diy_page()` — 913 строк.
7. Остальные (`servers_page`, `themes_page`, `claude_page`,
   `notebook_page`, `player_pop` / `/player/pop`, `_debts_page_html`,
   `sebastian_page`, `diy_article_page`) — можно группами, они заметно
   меньше.
8. Только после того как ВСЕ шаблоны вынесены — разложить сами роуты
   (Python-логика без HTML) по blueprint'ам. Это отдельный, последний
   шаг: сначала убрать вес шаблонов, потом уже резать логику.

## Шаг для одной страницы (повторяется на каждом пункте выше)

1. `git checkout -b codex/split-<имя-страницы>` от актуального dev-branch.
2. Найти строку с `html = """..."""` для этой функции, вырезать ТОЛЬКО
   содержимое строки в `templates/<имя>.html` (или `.js` для
   `vg_player_js`), заменить в `app.py` на чтение файла + те же
   подстановки, что были.
3. Проверки — обязательно все три:
   - `python3 -c "import ast; ast.parse(open('app.py').read())"`
   - `python3 scratchpad/jscheck.py` (или актуальный путь к нему)
   - Живой прогон: `scratchpad/run.sh`, зайти на именно эту страницу
     руками (или Playwright-сценарий, если есть готовый под неё в
     `scratchpad/`), убедиться, что выглядит и работает так же, как до
     переноса — включая куски, которые легко сломать незаметно: `%%NET%%`
     подстановка, кэш-заголовки (если страница их выставляет), любые
     built-in тесты из `scratchpad/*.js`, которые касаются этой страницы
     (список — в `CLAUDE.md`, у каждой фичи указаны свои тестовые файлы).
4. `git diff` посмотреть глазами: **диф должен быть маленьким** — по сути
   «строка стала read_text() файла», а не изменение самого содержимого.
   Если diff самого HTML/JS-контента не нулевой (не считая переноса в
   файл) — что-то пошло не так, разбираться, а не коммитить.
5. Коммит с понятным сообщением («перенос шаблона cabinet.html в
   отдельный файл, без изменения поведения»), пуш, дать Claude
   отревьюить диф перед мержем в dev-branch (маленький диф — дешёвое
   ревью).

## Итоговый шаг — blueprints (после того как все шаблоны вынесены)

Когда `app.py` уже не тащит HTML/JS, резать сам Python на blueprint'ы —
тоже по одному разделу за раз:
1. Создать `blueprints/<раздел>.py`, перенести туда роуты этого раздела
   (`@app.route` → `@bp.route`, `bp = Blueprint(...)`).
2. Перенести локальные хелперы, которые используются ТОЛЬКО в этом
   разделе, вместе с роутами; общие (auth, gzip, форматирование) оставить
   в `app.py` или вынести в `common.py`, импортировать оттуда.
3. `app.py`: `app.register_blueprint(cabinet_bp)` и т.д.
4. Те же три проверки, что и для шаблонов, плюс — что все URL остались
   ровно те же (`/api/diag` и т.п. — сверить список роутов
   `grep -n '@app\.\(route\|get\|post\)' app.py` до и после,
   их должно быть 97 суммарно по всем blueprint'ам).

## Что НЕ делать

- Не менять поведение, имена переменных, структуру данных «заодно, раз
  открыл файл» — это отдельная задача, не текущая.
- Не сжимать/переписывать шаблоны в Jinja-стиль с `{{ }}` (см. раздел про
  риски выше).
- Не объединять несколько страниц в один коммит — тогда откат одной
  страницы откатывает и остальные.
- Не запускать тяжёлый Playwright-прогон по всему сайту после каждого
  файла — только по странице, которую только что перенесли; полный
  прогон — перед финальным мержем в main.
